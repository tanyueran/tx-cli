# 开发笔记：问题与设计决策

> 记录 tx-cli 开发过程中遇到的关键问题与设计取舍，作为 [ARCHITECTURE.md](./ARCHITECTURE.md) 的补充——那里写「是什么」，这里写「为什么这么做、踩过什么坑」。

## 1. 自有的深度思考档位如何兼容不同供应商

**问题**：各家服务的「思考」协议互不兼容——OpenAI 官方用 `reasoning_effort`（档位即强度），火山方舟 / 智谱用 `thinking: { type }` 开关式，阿里 DashScope 用 `enable_thinking: boolean` 开关式，DeepSeek 则没有思考字段（靠换 reasoner 类模型）。

**决策**：编排层只面向统一的四档抽象 `off / low / medium / high`，协议差异全部收敛在 `core/llm/thinking.ts` 适配层翻译：

- 按 `baseUrl` 自动推断协议风格（`volces.com` / `doubao` / `bigmodel.cn` → `thinking`，`dashscope.aliyuncs.com` → `enable_thinking`，其余 → `reasoning_effort`）。注意推断依据是**服务地址**而非模型名称；推断不准时可用 `llm.thinkingStyle` 显式覆盖
- `llm.thinkingEffortMap` 高级映射兜底：适配只支持部分档位的服务（如把 low/medium/high 都映射成服务端唯一的 high）
- `off` 最大化兼容：在 reasoning_effort / none 风格下不下发任何思考字段，避免向不支持思考扩展的服务发送多余字段导致请求失败

**取舍**：开关式风格的服务上 low/medium/high 无差别（均按「开启」折算），此时黄字警告告知用户，避免误以为 high 真实生效。

## 2. 大模型 API 协议的选择

**问题**：接哪家协议，决定了对供应商的锁定程度与能力的上限。

**决策**：不考虑接入 Claude（Anthropic 协议），统一走 **OpenAI 兼容协议**；在 OpenAI 的 Chat Completions 与 Responses 之间选择了 **Responses API 无状态模式**（`store: false`）：

- 思考内容与正文在流式事件上天然分流（`reasoning_text.delta` / `reasoning_summary_text.delta` 与 `output_text.delta`），渲染层不需要从文本流里猜思考与正文的边界
- 无状态：服务端不留存会话，多轮历史由本地维护、每轮全量发送，不依赖任何服务端会话能力——因此任何支持该接口的 OpenAI 兼容服务（DeepSeek、Kimi、GLM、vLLM 等）都能直接接入

**代价**：要求所配置的服务支持 Responses API（而非仅有 Chat Completions），文档中已注明该前提。

## 3. 权限安全的设计

**问题**：让模型执行 bash 和写文件，必须把「模型失控删库 / 泄密」的风险压到最低。

**决策**：**三档沙箱 × 三种审批策略**正交组合：

- 沙箱档位：`read-only`（默认，全禁写全禁网）/ `workspace-write`（仅可写工作空间，bash 网络走域名白名单）/ `danger-full-access`（无隔离）
- 审批策略：`always-ask`（每次询问）/ `on-failure`（默认，沙箱拦截失败时询问升级重跑）/ `never`（从不询问——来自配置文件时仅在信任目录内生效，否则交互确认信任或降级；命令行显式指定不受限）
- 不同档位映射不同的文件系统边界（禁写、禁读 `~/.ssh` 等凭据目录）与网络限制（allow-only 白名单）

**两个容易被忽略的点**：

- **防自证信任**：项目 `.tx-cli/config.json` 随仓库分发，不能作为权限放大的凭据——项目配置仅可收紧沙箱能力，放宽类字段被忽略并告警
- **fs 工具的应用层边界**：fs 工具是进程内代码、不经 OS 沙箱进程，所以权限门卫在规则放行后还要按档位逐路径校验兜底（OS 沙箱只管得住子进程）

## 4. 内置工具的设置

**问题**：模型只有「手脚」齐全才能完成任务，但工具集又不能无限膨胀。

**决策**：提供固定的内置工具集（随版本发布，不支持运行时动态注册，保持轻量可控）：

| 类别 | 工具 | 说明 |
|---|---|---|
| 读查 | `read_file` / `list_dir` / `glob` / `grep` | 本地文件读取与检索 |
| 写 | `write_file` / `edit_file` | 整体写入 / 精确字符串替换（片段不唯一即失败，防误改）；受沙箱可写边界管控 |
| 联网 | `web_search` | 搜索实时信息 |
| 执行 | `bash` | 仅 agent 装配，受沙箱与审批管控 |
| 规划 | `write_todos` | 任务清单，仅 agent 装配 |

**配套机制**：统一 `Tool` 接口 + 权限门卫包装；执行器统一处理参数解析（失败回传模型重试）、超时（审批问询期间暂停计时，用户思考时间不计入）、输出截断（8192 字符，防撑爆上下文）、错误转 `ok:false` 回传模型自纠（工具错误不中断会话）。

## 5. Skill 的加载和使用

**问题**：技能手册全文常驻系统提示词会浪费 token；完全不注入模型又不知道技能存在。

**决策**：**渐进式披露**两级加载：

1. 启动时扫描 `~/.tx-cli/skills`（用户级）与 `./.tx-cli/skills`（项目级，同名时项目级优先）中的 `SKILL.md`，仅把**名称和描述**装配进系统上下文
2. 发现技能时才装配 `load_skill` 工具（空技能不多下发工具定义），模型命中具体技能后调用它加载技能正文与路径，再按手册指引执行

## 6. MCP 的管理和加载

**问题**：内置工具不可能覆盖所有场景，需要标准化的外部工具扩展机制。

**决策**：配置文件 `mcpServers` 段（全局 + 项目两层按服务器名合并，同名以项目为准），支持 stdio（本地子进程）与 http（Streamable HTTP）两类；会话启动时连接所有服务器，**拉取各服务器的工具定义**（`listTools`，工具名带 `mcp__<服务器名>__<工具名>` 前缀与内置工具隔离）装配进工具清单，模型按需调用。

**两处容易误解的点**：

- MCP 加载的是**工具定义**而非提示词——进入系统上下文的只有各工具的 description
- MCP **不是无条件可信**：它不经 OS 沙箱，判定独立于沙箱档位——声明 `readOnlyHint` 的只读工具默认放行，可写工具默认需要审批（支持「始终允许该服务器」的服务器级授权，落盘到项目配置 `mcp.rules.allow`）；单个服务器连接失败只黄字告警，不影响其他服务器

## 7. chat 和 agent 的界限

**问题**：合成一个命令太重（简单问答也要背沙箱 / MCP 的复杂度），拆成两个命令又需要划清边界。

**决策**：两个命令**共用同一套会话机制**（差异收敛为一份模式配置 `ConversationModeConfig`，即「模式即配置」），边界按用途划分：

| 维度 | chat | agent |
|---|---|---|
| 用途 | 回答问题（轻量只读） | 执行与完成任务 |
| 写侧工具 | 代码强制剔除（只读语义写死，不依赖沙箱档位） | 装配 |
| bash | 不装配 | 装配（沙箱 + 审批管控） |
| MCP | 硬编码关闭 | 缺省开启（`--no-mcp` 按次关闭） |
| 工具调用轮数上限 | 8 轮（问答不该打转） | 20 轮（任务允许多步） |
| 思考档位兜底 | `low` | `medium` |

轮数上限不是硬截断：达到上限后收走工具定义再跑最后一轮（软收敛），模型基于已有信息直接作答并黄字提示。

## 8. 命令的提示和补全

**问题**：REPL 的输入体验（补全、编辑、历史）决定工具的「手感」，但引入重量级 TUI 框架会显著增加体积与依赖。

**决策**：分两层实现：

- **REPL 输入行**：基于 Node 原生 `readline` API 自实现——keypress 事件驱动的编辑与光标移动（代理对感知，一次退格跨过整个 emoji）、bracketed paste 粘贴支持、补全面板（最多 10 条建议：内联命令与技能名）
- **交互问答**（审批、确认、选择、信任询问）：统一封装 `prompts` 库（`shared/interactive-prompt.ts`）。封装的核心价值是统一**取消语义**——原生 prompts 被取消时只返回缺字段的对象，调用方极易误把空值当默认值继续执行；封装后在 `onCancel` 同步回调中抛 `CancelError` 并标记回合取消，保证「取消一轮即中止整轮」的时序可靠性
